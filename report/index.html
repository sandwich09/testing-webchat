Webchat มีหน้าใส่รหัสกั้นไว้ รหัสผมแนบไปในอีเมลฉบับเดียวกับลิงก์หน้านี้ ไม่ได้เก็บไว้ใน repo

  1. เพิ่มเพื่อน LINE OA จากมือถือ จะมีการ์ดต้อนรับเด้งมาพร้อมปุ่มสามปุ่ม
  2. เปิด Webchat แล้วใส่รหัส ชื่อกับรูปโปรไฟล์ LINE ของคุณจะโผล่ในรายชื่อทางซ้าย
  3. พิมพ์อะไรก็ได้จาก LINEสองสามวินาทีข้อความจะขึ้นใน Webchat ส่งรูป สติกเกอร์ หรืออัดเสียงมาด้วยก็ได้
  4. กดที่ชื่อตัวเองใน Webchat แล้วตอบกลับข้อความจะไปขึ้นใน LINE ถ้าอยากส่งรูปหรือวิดีโอ กดไอคอนรูปภาพข้างช่องพิมพ์
  5. กลับไปที่ LINE แล้วกด "คุยกับ AI"ลองถามราคาเมนูกาแฟดู ผมใส่เมนูร้านกาแฟสมมติไว้ในคลังความรู้ จากนั้นลองถามเรื่องที่ไม่เกี่ยว จะเห็นว่ามันไม่เดา
  6. กด "คุยกับแอดมิน"AI จะหยุดตอบ ฝั่ง Webchat แชทนั้นจะขึ้นป้ายรอแอดมิน

Webchat สำหรับแอดมินที่ดูแล LINE Official Account หนึ่งบัญชี

ระบบนี้เป็นตัวกลางระหว่าง LINE OA กับแอดมิน ข้อความที่ผู้ใช้ส่งเข้ามาทาง LINE จะมารวมอยู่ในหน้า Webchat แยกเป็นแชทรายคน แอดมินเห็นชื่อและรูปโปรไฟล์ของผู้ส่ง เลือกแชทแล้วตอบกลับได้จากหน้าเดียว คำตอบจะไปถึงผู้ใช้ใน LINE

รายชื่อ

เรียงตามคนที่ทักเข้ามาล่าสุด ไม่ได้เรียงตามข้อความล่าสุดรวม ๆ เพราะถ้าแอดมินตอบใครไป คนนั้นจะเด้งขึ้นบนทั้งที่ไม่มีอะไรต้องทำต่อ มีแท็บกรองคนที่ยังไม่ได้อ่านกับคนที่รอแอดมิน และค้นจากชื่อได้

ชื่อกับรูปดึงจาก LINE ตอนเจอกันครั้งแรก หลังจากนั้นถ้าเขาทักมาอีกและข้อมูลเก่าเกินหนึ่งวัน ระบบจะดึงใหม่ให้

การส่งข้อความ

LINE มีสองทางให้ส่ง คือ reply ซึ่งไม่นับโควตาข้อความ แต่ต้องใช้ token ที่มากับข้อความของผู้ใช้และหมดอายุเร็ว กับ push ซึ่งนับโควตา ระบบจะลอง reply ก่อนเสมอ ถ้า token ใช้ไม่ได้แล้วค่อย push

ข้อความที่ส่งมีสถานะให้เห็นว่ากำลังส่ง ส่งแล้ว หรือไม่สำเร็จ ถ้าไม่สำเร็จมีปุ่มส่งซ้ำ ตรงนี้มีเรื่องต้องระวังคือคำขอแรกอาจไปถึง LINE แล้วแต่เราไม่ได้คำตอบกลับ ถ้าส่งซ้ำเฉย ๆ ผู้ใช้จะได้สองข้อความ ผมเลยแนบ retry key ตัวเดิมไปทุกครั้ง LINE จะรู้เองว่าเป็นข้อความเดียวกัน

ของเล็ก ๆ ที่เพิ่ม

  • ถ้าผู้ใช้กดตอบกลับข้อความไหนใน LINE ฝั่ง Webchat จะเห็นว่าเขาอ้างถึงข้อความอะไร
  • แอดมินจดโน้ตของแต่ละคนได้ โน้ตอยู่ในระบบเราเท่านั้น ไม่ถูกส่งไป LINE และ AI ก็ไม่เห็น

โจทย์ไม่ได้ขอ แต่แชทที่ส่งรูปไม่ได้ผมว่าใช้จริงลำบาก

ทิศรับอะไรได้ใหญ่สุด
จาก LINEรูป วิดีโอ เสียง สติกเกอร์รูป 10 MB · เสียง 20 MB · วิดีโอ 50 MB
จาก Webchatรูป JPEG, PNG, WebP, HEIC และวิดีโอ MP4รูป 10 MB · วิดีโอ 50 MB

ระบบดูชนิดไฟล์จากเนื้อไฟล์จริง ไม่เชื่อนามสกุล เพราะเปลี่ยนชื่อไฟล์เป็น .jpg ใครก็ทำได้ ส่วนรูป HEIC จาก iPhone ซึ่ง LINE ไม่รับ จะถูกแปลงเป็น JPEG ใน browser ก่อนส่ง

ไฟล์ที่ผู้ใช้ส่งมาจาก LINE ต้องดึงมาเก็บเองภายในเวลาที่ LINE ยังเก็บไว้ให้ ระบบทำขั้นนี้หลังตอบ webhook ไปแล้ว ข้อความจึงเข้าเร็วเหมือนเดิม แล้วรูปตามมาทีหลังนิดหนึ่ง

ส่วนนี้เป็นส่วนที่พังบน production สองครั้ง ทั้งที่ test pass หมด ผมเล่าไว้ในหน้า ปัญหาที่เจอ

เปิดไว้แล้ว Claude จะตอบแทนแอดมิน สิ่งที่ผมคิดเยอะคือจะหยุดมันได้ยังไง

การเปิดปิด

มีสวิตช์สองชั้น ชั้นแรกเป็นรายแชท แอดมินเปิดเองหรือผู้ใช้กดปุ่มใน LINE ก็ได้ ชั้นที่สองคือสวิตช์รวมในหน้าตั้งค่า ปิดแล้วหยุดทุกแชททันที เอาไว้ใช้ตอน AI ตอบเพี้ยนแล้วไม่มีเวลาไล่ปิดทีละคน

อีกกรณีคือแอดมินเข้ามาตอบเอง AI ของแชทนั้นจะปิดให้เลย ไม่งั้นจะมีสองเสียงตอบผู้ใช้คนเดียวกัน

การส่งต่อให้แอดมิน

ถ้าถามเรื่องที่ไม่มีในคลังความรู้ ขอให้ทำอะไรที่ต้องใช้คน หรือส่งรูปกับเสียงมา AI จะบอกผู้ใช้ว่าเดี๋ยวแอดมินมาดูให้ แล้วแชทนั้นขึ้นป้ายรอแอดมินในรายชื่อ ผมตั้งใจให้มันยอมแพ้ง่ายหน่อย ดีกว่าเดาแล้วผิด

การตั้งค่า

  • ชื่อที่ AI ใช้เรียกตัวเอง คำลงท้าย และคำแนะนำเพิ่มว่าให้คุยแบบไหน
  • โมเดล เลือกได้ระหว่าง Opus 5.5, Sonnet 5.5 และ Haiku 5.5
  • งบต่อวัน ใช้ถึงแล้ว AI หยุดจนถึงเที่ยงคืน มีหน้าดูว่าแต่ละข้อความใช้ไปเท่าไหร่

สองอย่างที่กำหนดว่า AI รู้อะไร และยอมคุยเรื่องอะไร

คลังความรู้

แอดมินอัปโหลด PDF แล้ว Claude อ่านออกมาเป็นข้อความเก็บไว้ ตอนตอบระบบส่งทั้งคลังไปพร้อมคำถาม ไม่ได้ทำ embedding หรือระบบค้นหา

ผมเลือกแบบนี้เพราะคลังของบัญชีเดียวมันเล็ก จำกัดไว้ที่ 50,000 token ส่งทั้งก้อนง่ายกว่ามากและไม่มีโอกาสค้นพลาด ถ้าวันหนึ่งคลังโตเกินนี้ค่อยเปลี่ยน

ไฟล์รับได้ไม่เกิน 4 MB และ 30 หน้า แอดมินเปิดดูได้ว่า Claude อ่านออกมาเป็นอะไร เผื่อ PDF เป็นภาพสแกนแล้วอ่านเพี้ยน

ขอบเขตหัวข้อ

เปิดแล้ว AI จะคุยแค่หัวข้อที่แอดมินใส่ไว้ วิธีทำคือมีการเรียกโมเดลอีกครั้งหนึ่งก่อน เพื่อถามว่าข้อความนี้อยู่ในหัวข้อไหม ผ่านแล้วถึงส่งให้ตัวที่ตอบจริง

ที่ต้องแยกเป็นสองตัว เพราะตัวที่ตอบผู้ใช้โดนพูดหว่านล้อมได้ ส่วนตัวคัดกรองไม่ได้คุยกับใคร มันตอบได้แค่ผ่านหรือไม่ผ่าน เลยหลอกยากกว่า และถ้าตัวคัดกรองล่มหรือไม่แน่ใจ ผมให้ถือว่าไม่ผ่าน

ให้ผู้ใช้เลือกเองว่าจะคุยกับ AI หรือกับคน

สองภาพนี้ถ่ายจาก production ปุ่มในการ์ดกับปุ่มใน rich menu ด้านล่างจอทำงานเหมือนกัน

  • คุยกับ AI เปิด AI ให้แชทนั้น แล้ว AI ทักก่อน
  • คุยกับแอดมิน ปิด AI แล้วขึ้นป้ายรอแอดมินฝั่ง Webchat
  • วิธีทดสอบ ส่งข้อความแนะนำ แก้ข้อความได้จากหน้าตั้งค่า

ปกติจะตั้ง rich menu ต้องเข้า LINE Developers Console หรือยิง API เอง ผมทำปุ่ม publish ไว้ในหน้าตั้งค่าเลย กดครั้งเดียวระบบอัปโหลดรูปและผูกเมนูให้

การเชื่อม LINE OA

ใส่ Channel secret กับ access token ที่หน้าตั้งค่า ค่าทั้งสองถูกเข้ารหัสก่อนลงฐานข้อมูลและไม่แสดงกลับมาอีก ตอนกดบันทึกระบบจะถาม LINE ด้วยว่าสองค่านี้เป็นของ channel เดียวกันจริงไหม กันกรณี copy มาผิดบัญชี

แบบทดสอบนี้เห็นข้อความจริงที่ส่งมา เลยไม่อยากให้เข้าได้ทุกคนที่มีลิงก์

ทางเข้ามีรหัสเดียวใช้ร่วมกัน มี rate limit ใส่ได้ 5 ครั้งต่อนาที เกินแล้วต้องรอก่อนถึงจะลองใหม่ได้ ใส่ถูกแล้วได้ cookie ที่ JavaScript อ่านไม่ได้

ฝั่ง webhook ใครก็ยิงเข้ามาได้ถ้ารู้ URL ทุกคำขอจึงต้องมีลายเซ็นของ LINE ที่คำนวณจาก Channel secret ไม่ตรงคือทิ้ง

อีกเรื่องที่ระวังคือ prompt injection ผู้ใช้พิมพ์ประโยคอย่าง "ลืมคำสั่งก่อนหน้า" เข้ามาได้ และใน PDF ที่อัปโหลดก็ซ่อนประโยคแบบนี้ไว้ได้เหมือนกัน ระบบจึงส่งข้อความของผู้ใช้กับเนื้อหาใน PDF ให้ AI ในฐานะข้อมูล ไม่ใช่คำสั่ง และบอก AI ไว้ชัดเจนว่าถ้าเจอประโยคสั่งการในนั้นให้เพิกเฉย

ส่วน log ของระบบเก็บแค่ว่าเกิดอะไรขึ้นและเกิดกับแชทไหน เช่น ส่งสำเร็จหรือล้มเพราะอะไร ไม่เก็บตัวข้อความที่คุยกัน เพราะทุกคนที่เข้า dashboard ของ Vercel ได้จะอ่าน log ได้ ซึ่งอาจเป็นข้อมูลอ่อนไหว

สมมติมีคนพิมพ์ "สวัสดี" เข้ามาใน LINE

  1. LINE ยิง webhook มาที่เราระบบเช็กลายเซ็นก่อนอย่างอื่น โดยคำนวณจาก body ดิบที่ยังไม่ได้ parse
  2. เช็กว่าเคยได้ข้อความนี้แล้วหรือยังถ้าเปิด webhook redelivery ไว้ LINE จะส่ง event เดิมมาอีกรอบเมื่อรอบแรกเรารับไม่สำเร็จ ระบบจำรหัสของ event ไว้ ได้ซ้ำก็ไม่เก็บซ้ำ
  3. เก็บลงฐานข้อมูล แล้วตอบ LINE ว่าได้แล้วทั้งหมดนี้ไม่ถึงวินาที งานที่ใช้เวลานานอย่างดึงรูปหรือเรียก AI แยกไปทำหลังตอบแล้ว request จึงไม่ timeout
  4. งานที่ช้าทำทีหลังถ้าเป็นรูปก็ไปดึงมาเก็บ ถ้าเปิด AI ก็ให้ Claude คิดคำตอบ สองอย่างนี้รันหลังจากตอบ LINE ไปแล้ว
  5. หน้า Webchat ถามหาข้อความใหม่ถามเป็นรอบ ๆ และขอแค่สิ่งที่เปลี่ยนตั้งแต่รอบก่อน ไม่ได้โหลดใหม่ทั้งหน้า
  6. แอดมินตอบลอง reply ก่อน ไม่ได้ก็ push แล้วอัปเดตสถานะกลับมาที่หน้าจอ

ข้อ 5 หลายคนอาจถามว่าทำไมไม่ใช้ WebSocket คำตอบคือ function บน Vercel ถือ connection ค้างไว้นาน ๆ ไม่ได้ จะทำ real-time ต้องเพิ่มบริการอีกตัว ซึ่งสำหรับแอดมินไม่กี่คน ช้าไปสองสามวินาทียังรับได้ ผมเลยเลือกทางที่มีชิ้นส่วนน้อยกว่า

ผมใช้ architecture ตั้งต้นแบบ hexagonal

แนวคิดของ hexagonal คือให้ business logic อยู่ใน core และไม่รู้จักโลกภายนอก core ไม่รู้ว่าข้อความมาจาก LINE ไม่รู้ว่า AI คือ Claude และไม่รู้ว่าข้อมูลเก็บใน PostgreSQL มันรู้จักแค่ port ซึ่งเป็น interface เช่น "ที่ส่งข้อความ" หรือ "ที่เก็บข้อมูล" ส่วนของจริงเป็น adapter ที่ implement port นั้นแล้ว inject เข้ามาจากข้างนอก

โครงของ repo
  • src/source code ของแอป
  • core/corebusiness logic ไม่มี I/O และไม่ import จาก layer อื่น
  • domain/model, type และ pure function
  • use-cases/application logic ทีละ use case เช่น รับ event จาก LINE ส่งข้อความ ให้ AI ตอบ
  • ports/interface ที่ core ต้องการจากข้างนอก เช่น MessagingGateway, MessageRepository
  • adapters/adaptersimplementation ของแต่ละ port
  • line/LINE Messaging API: ตรวจ signature ของ webhook, reply และ push
  • claude/Claude API: chat model, PDF extraction และ topic guard
  • prisma/repository บน PostgreSQL
  • blob/file storage บน Vercel Blob
  • local-storage/file storage ลง disk สำหรับ local development
  • system/clock, ID generator, logger และ crypto
  • fakes/in-memory implementation ของทุก port สำหรับ unit test
  • contracts/sharedzod schema ของ request และ response ใช้ร่วมกันทั้ง client และ server
  • composition/composition root: ผูก adapter เข้ากับ use case, อ่าน env และ route wrapper
  • features/UIReact component และ hook แยกตาม feature
  • access/หน้าใส่ access code
  • inbox/หน้าแชท: contact list, thread และ composer
  • settings/หน้าตั้งค่า
  • common/UI primitive, font และ API client ที่ใช้ร่วมกัน
  • app/App Router ของ Next.js
  • api/Route Handler ทั้งหมด รวม webhook ของ LINE
  • prisma/toolingschema และ migration
  • e2e/E2E test ด้วย Playwright
  • stubs/stub server ของ LINE และ Claude สำหรับ test และ local development
  • scripts/script ตรวจ migration, ตรวจ docs และ AI eval
  • docs/spec, ADR, runbook และ test report

สีในผังแบ่งตาม layer: ชมพูคือ core, ฟ้าคือ adapter ที่ต่อกับ service ข้างนอก, เหลืองคือส่วนที่ผูก core กับ adapter เข้าด้วยกัน, เขียวคือ UI และ route ส่วนสีเทาอยู่นอก src เป็น tooling สำหรับ development และ test ทิศของ dependency ชี้เข้าหา core เสมอ และมี lint rule บังคับ ถ้า core import จาก adapter CI จะ fail

ยอมรับว่าสำหรับแบบทดสอบ โครงนี้ค่อนข้างเยอะ ที่ผมยังเลือกเพราะระบบนี้พึ่ง service ข้างนอกสามเจ้า และผมไม่อยากให้ test ต้องยิง LINE หรือ Claude จริงทุกครั้ง พอ core ไม่ผูกกับใคร ก็ unit test ได้ด้วย fake ใน memory รันสองพันกว่าข้อจบในสิบวินาที

จุดที่กลัวคือ fake จะทำงานไม่เหมือนของจริง แล้ว test pass แบบหลอก ๆ เลยเขียน contract test ชุดเดียวต่อหนึ่ง port แล้วรันกับทั้ง fake และ adapter จริงบน PostgreSQL ถ้าสองฝั่งทำงานต่างกัน test จะ fail

Design decision ที่มีทางเลือกมากกว่าหนึ่ง และ trade-off ของทางที่ผมเลือก

เรื่องเลือกไม่เลือกเหตุผล
อัปเดตหน้าจอPolling ทุกไม่กี่วินาที โดยขอเฉพาะแถวที่เปลี่ยนตั้งแต่รอบก่อนWebSocket, SSEServerless function ถือ connection ค้างไม่ได้ ต้องเพิ่ม service อีกตัว แลกกับ latency สองสามวินาที
Webhookเก็บ event แล้วตอบ 200 ทันที งานที่ช้าไปทำใน after()ทำทุกอย่างให้จบใน requestงานอย่างดึงรูปหรือเรียก AI ใช้เวลานาน ถ้าทำใน request webhook จะ timeout และเมื่อเปิด webhook redelivery ไว้ LINE จะส่ง event เดิมมาซ้ำ

Topic guardClassifier แยกหนึ่ง call ก่อนถึง chat model และ fail closedใส่กฎใน system prompt อย่างเดียวChat model โดน prompt injection ได้ Classifier ที่ตอบได้แค่ผ่านหรือไม่ผ่านโดนยากกว่า
Inbound mediaBuffer ใน memory แล้ว upload เป็น body เดียวPipe stream จาก LINE เข้า BlobStream ค้างบน production จน function timeout

วิธีรัน

  • Script เรียก Messages API จริง ผ่าน prompt builder ตัวเดียวกับที่ production ใช้ ไม่ได้ก๊อป prompt มาแปะแยก
  • Workflow แยกบน GitHub Actions ชื่อ ai-eval เป็น workflow_dispatch ที่ต้องติ๊ก confirm เอง เพราะมีค่าใช้จ่าย ก่อนรันมี preflight เช็กว่า API key ยังใช้ได้ แล้วรันเป็น matrix สามโมเดล

  • Rule-based grader ตัดสินด้วย pattern matching บนข้อความคำตอบ ไม่ได้ใช้ LLM เป็น judge ผลจึงรันซ้ำได้โดยไม่เสียเงินเพิ่ม แต่ก็ผิดได้ ดูหัวข้อถัดไป

ต้องบอกก่อนว่ารอบแรกไม่ได้ออกมาสวยแบบนี้ fail กันโมเดลละสี่ถึงหกข้อ พอไปอ่านคำตอบทีละข้อถึงเห็นว่า AI ตอบถูก แต่ grader ของผมเองที่ผิด มันตรวจด้วยการจับคำ เช่น ถ้าคำตอบมีคำว่า "ฟรี" ถือว่า AI ยืนยันของฟรี ทั้งที่ประโยคเต็มคือ "ไม่มีข้อมูลเรื่องโปรโมชันเค้กฟรี"

ผมแก้เกณฑ์หกข้อแล้วรันใหม่ ได้ผลตามตาราง และเก็บคำตอบจริงของทั้งหกข้อเป็น regression test ของ grader คู่กับคำตอบที่ต้อง fail จริง เพื่อไม่ให้เกณฑ์หลวมเกินไป ข้อที่ Haiku ยัง fail ก็เป็นแบบเดียวกัน ซึ่งแก้แล้วแต่ไม่ได้รันซ้ำอีกรอบ เพราะไม่อยากรันไปเรื่อย ๆ จนกว่าจะเขียวทุกช่อง

สรุปคือชุดนี้ใช้ดูได้ว่าเปลี่ยน prompt แล้วดีขึ้นหรือแย่ลง แต่ 27 ข้อน้อยเกินกว่าจะเอาไปอ้างเป็นสถิติ และคำตอบของโมเดลไม่เหมือนกันทุกครั้ง ข้อเดียวกัน pass รอบหนึ่งแล้ว fail อีกรอบได้

สามเรื่องที่ test pass หมด แต่พังตอนลองกับของจริง

รูปจาก LINE ค้างที่ "กำลังโหลดรูป"

ส่งรูปจากมือถือแล้วฝั่ง Webchat หมุนอยู่อย่างนั้นไม่จบ ตอนแรกสงสัยว่าหน้าเว็บไม่อัปเดต พอไปดูในฐานข้อมูลถึงรู้ว่ารูปไม่เคยถูกเก็บเลย แล้ว log ของ Vercel ก็เฉลยว่า function โดนตัดเพราะรันครบ 300 วินาที

ต้นเหตุอยู่ที่ผมต่อท่อจาก LINE ตรงเข้า Vercel Blob แบบ stream ซึ่งดูประหยัดหน่วยความจำดี แต่มันค้าง ที่ไม่เห็นก่อนหน้านี้เพราะเคยลองแต่กับไฟล์เสียงสี่วินาที ซึ่งเล็กจนผ่านไปได้

ผมแก้ให้อ่านไฟล์เข้าหน่วยความจำให้ครบก่อนแล้วค่อยส่ง ใส่เพดานเวลาทุกขั้น และเพิ่ม log ว่าถึงขั้นไหนแล้ว คราวหน้าถ้าค้างอีกจะรู้ทันทีว่าค้างตรงไหน ไม่ต้องเดา

วิดีโอจาก Webchat ส่งไม่ได้

เลือกไฟล์ MP4 แล้วหน้าเว็บบอกว่าไม่รองรับ ทั้งที่เป็น MP4 แท้ ๆ

ไฟล์ MP4 มีรหัสสี่ตัวอักษรในหัวไฟล์บอกว่าเป็น version ไหน ผมเขียนให้หน้าเว็บรู้จักไว้หก version ไฟล์ที่ใช้ลองเป็น version ที่เจ็ด ที่น่าหงุดหงิดคือฝั่ง server รับได้อยู่แล้ว แต่ไฟล์ไปไม่ถึงเพราะโดนหน้าเว็บกันไว้ก่อน แก้โดยให้สองฝั่งใช้กฎเดียวกัน

รูปโปรไฟล์ไม่ขึ้น

ทุกคนเป็นวงกลมตัวอักษรย่อ พอเปิด console ดูก็เจอ error แดงเป็นแถว

LINE เก็บรูปโปรไฟล์ไว้สอง host แต่ผมอนุญาตไว้ใน Content Security Policy แค่ host เดียว เพิ่มอีก host ก็จบ

สิ่งที่ได้เรียนรู้

สามเรื่องนี้เหมือนกันตรงที่ตัวจำลองของผมไม่เหมือนของจริงพอ ไฟล์ในตัวจำลองเล็กเกิน และ URL ก็เป็นแบบเดียว ตอนนี้ทั้งสามกรณีอยู่ใน test แล้ว แต่ที่ผมได้จริง ๆ คือต่อให้ test เขียวเป็นพันข้อ ก็ยังต้องหยิบมือถือมาลองเองอยู่ดี

ของที่ยังไม่ได้ลอง กับของที่ตั้งใจไม่ทำ

ยังไม่ได้ลอง

  • Firefox กับ Safari ผมลองแค่ Chrome
  • หน้าเว็บบนมือถือจริง ที่ผ่านมาใช้โหมดจำลองของ browser
  • คนใช้พร้อมกันเยอะ ๆ ไม่ได้ทำ load test
  • ตอนที่ LINE ล่มหรือช้าจริง ๆ ลองแค่กับตัวจำลอง

ตั้งใจไม่ทำ

  • ระบบบัญชีรายคน ตอนนี้ใช้รหัสเดียวร่วมกัน
  • ต่อหลาย LINE OA ในระบบเดียว
  • อัปเดตหน้าจอแบบ real-time ตอนนี้ช้าได้สองสามวินาที
  • ให้ AI ดูรูปหรือฟังเสียง เจอแล้วมันจะส่งต่อให้แอดมิน

ข้อจำกัดจาก LINE

ถ้าผู้ใช้กดปุ่มใน rich menu LINE จะแสดงบับเบิลข้อความฝั่งเขา แต่ไม่ส่งรหัสของบับเบิลนั้นมาให้เรา ถ้าเขากดตอบกลับโดยอ้างถึงบับเบิลนั้น Webchat จะรู้แค่ว่ามีการอ้างถึง แต่ไม่รู้ว่าอ้างถึงอะไร ผมหาทางแก้ฝั่งเราไม่ได้

# การเชื่อมต่อ LINE

> สถานะ: สร้างแล้ว · อัปเดตล่าสุด: 2026-11-19

## เป้าหมาย

รับทุกอย่างที่ลูกค้าส่งมาทาง LINE OA โดยไม่ตกหล่นและไม่ซ้ำ และส่งข้อความของแอดมินและ AI กลับไปโดยลูกค้าไม่ได้รับซ้ำ

ทุกการเรียก LINE ผ่าน port `MessagingGateway` ด้วย `fetch` ตรงกับ Messaging API ไม่ใช้ SDK

## รับ event (webhook)

1. อ่าน raw body เป็นข้อความ
2. ตรวจ header `x-line-signature` ด้วย HMAC-SHA256 จาก Channel secret และเทียบแบบ timing-safe ถ้าไม่ผ่านตอบ 401 และบันทึกเหตุการณ์ด้านความปลอดภัย
3. ตรวจ body ด้วย schema ที่เข้มเฉพาะ field ที่ใช้ และปล่อยผ่าน field อื่น
4. แต่ละ event ประมวลผลแยกกัน event หนึ่งพังไม่กระทบ event อื่น
5. Event ที่ `webhookEventId` ซ้ำถูกข้าม และข้อความที่ `lineMessageId` ซ้ำไม่ถูกบันทึกอีก โดยใช้การ insert แบบข้ามเมื่อซ้ำ
6. เมื่อ signature ถูกต้อง ตอบ 200 แม้บาง event พลาด ยกเว้นกรณีเดียว: ทุก event ในก้อนล้มเหลว ไม่มีอะไรถูกบันทึกเลย และฐานข้อมูลไม่ตอบ (`settings.ping` ล้ม) จึงตอบ 503 `db.unavailable` (body มีแค่รหัส ข้อความกลาง และ `requestId`) ให้ LINE ส่งทั้งก้อนซ้ำ ซึ่ง LINE ทำเฉพาะเมื่อเปิด "Webhook redelivery" ไว้ ([line-oa-setup ขั้นที่ 4](../runbooks/line-oa-setup.md#4-ตั้ง-webhook-ฝั่ง-line)) ก้อนที่ส่งซ้ำมี `deliveryContext.isRedelivery: true` และ `webhookEventId` เดิม ข้อ 5 จึงบันทึกแต่ละ event ครั้งเดียว ก้อนที่มีอย่างน้อยหนึ่ง event ถูกบันทึก หรือ event ล้มด้วยเหตุของตัวเองขณะฐานข้อมูลยังตอบ ตอบ 200 เพราะการส่งซ้ำไม่ช่วย ([use-cases ReceiveLineEvents](../architecture/use-cases.md#receivelineevents) ข้อ 7)
7. ถ้ายังไม่ได้ตั้ง credential ตอบ 401

## ชนิดของ event

| Event | ระบบทำอะไร |
| --- | --- |
| ข้อความตัวอักษร | บันทึก และเข้าเงื่อนไข AI ตอบแทน ถ้าลูกค้าใช้ "ตอบกลับ" ของ LINE กับข้อความใด `message.quotedMessageId` ถูกเก็บใน `Message.quotedLineMessageId` (หัวข้อ "ข้อความที่ตอบกลับ") |
| รูป, วิดีโอ | บันทึกทันที แล้วดาวน์โหลดเข้าที่เก็บไฟล์หลังตอบ 200 และแชทขึ้นสถานะรอแอดมินถ้า AI ตอบแทนเปิดอยู่ |
| สติกเกอร์ | บันทึก id และแสดงจาก URL ของ LINE |
| เสียง (`audio`) | บันทึกเป็นชนิด `audio` พร้อม `message.duration` (ms อ่านแบบผ่อนปรน ค่าที่ไม่ใช่จำนวนเต็มไม่ติดลบถือว่าไม่รู้) แล้วดาวน์โหลดเข้าที่เก็บไฟล์หลังตอบ 200 เหมือนรูปและวิดีโอ เสียงที่ `contentProvider.type` ไม่ใช่ `line` ไม่ถูกดึง (`failed`) ข้อความเสียงที่รับก่อน migration ที่เก้ายังเป็นชนิด `other` เป็นข้อความที่ไม่ใช่ตัวอักษร: เมื่อ AI ตอบแทนเปิด แชทขึ้นรอแอดมินด้วย `customer_sent_non_text` ไม่ถอดเสียงและไม่ส่งให้โมเดล |
| ไฟล์, ตำแหน่ง และอื่น ๆ | บันทึกเป็นชนิด `other` แสดงป้ายบอกประเภท ไม่ดาวน์โหลด |
| follow | สร้างหรืออัปเดต Contact เป็นติดตามอยู่ และส่งข้อความต้อนรับด้วย reply token ของ event นั้น (หัวข้อ "ข้อความต้อนรับ") |
| postback | ปุ่มของ rich menu หรือของข้อความต้อนรับ (หัวข้อ "Rich menu") data ที่แอปไม่ได้สร้างถูกเพิกเฉยพร้อม log `line.postback.ignored` ไม่บันทึกค่า |
| unfollow | ตั้งเป็นเลิกติดตามแล้ว และปิดช่องตอบ unfollow ที่เวลาเก่ากว่า follow หรือข้อความล่าสุดของลูกค้าถูกเพิกเฉย (event มาไม่เรียงได้เมื่อ LINE ส่งซ้ำ) |
| ข้อความหรือ postback จากลูกค้าที่เป็นเลิกติดตามแล้ว | ลูกค้าที่ส่งข้อความได้ยังเป็นเพื่อนอยู่ จึงตั้งกลับเป็นติดตามอยู่ที่เวลาของข้อความ และเพิ่มบรรทัดเหตุการณ์ `contact.followed` เหมือน follow ข้อความที่เก่ากว่า unfollow ไม่เปลี่ยนสถานะ |
| ชนิดที่ไม่รู้จัก | บันทึก log แล้วข้าม |

ระบบดึงชื่อและรูปจาก profile API เฉพาะลูกค้าที่เห็นครั้งแรก ภายใน request ก่อนตอบ webhook ด้วย timeout `LINE_PROFILE_TIMEOUT_MS` และไม่ retry ถ้าดึงไม่ได้ ระบบบันทึก Contact โดยไม่มีชื่อแล้วทำต่อ และหน้าเว็บแสดงตัวอักษรแทนรูป ([use-cases](../architecture/use-cases.md#receivelineevents))

## สื่อขาเข้า

- LINE เก็บไฟล์ของข้อความไว้ชั่วคราว จึงต้องดาวน์โหลดตอนรับ
- ดาวน์โหลดแบบ stream จาก host ของ LINE ที่กำหนดตายตัวเท่านั้น
- เฉพาะ HTTP 200 คือไฟล์ LINE ตอบ 202 (หรือ 2xx อื่น) เมื่อยังเตรียมไฟล์ไม่เสร็จ เช่น วิดีโอที่กำลัง transcode ระบบไม่อ่านคำตอบนั้นเป็นไฟล์ แต่รอ `MEDIA_NOT_READY_POLL_MS` แล้วถามสถานะที่ `GET /v2/bot/message/{id}/content/transcoding` (`processing`, `succeeded`, `failed`) ซ้ำ จนพร้อมจึงดาวน์โหลดอีกครั้ง ข้อความคง `pending` ระหว่างนี้เฉพาะเมื่องบ `MEDIA_JOB_BUDGET_MS` ยังพอสำหรับเวลาแย่ที่สุดของทุกขั้นที่เหลือ ถ้าไม่พอหรือ LINE บอกว่าล้มเหลว สื่อเป็น `failed` ทันที ([use-cases StoreInboundMedia](../architecture/use-cases.md#storeinboundmedia))
- รูปไม่เกิน `IMAGE_MAX_BYTES` และวิดีโอไม่เกิน `VIDEO_MAX_BYTES` เกินกว่านั้นไม่เก็บ (`mediaStatus` เป็น `too_large`) และแสดงป้ายว่าไฟล์ใหญ่เกิน
- ตรวจชนิดจากเนื้อไฟล์ เสียงรับ MPEG-4 (`ftyp` ที่ไม่ใช่ QuickTime โดย brand `M4A ` หรือ `M4B ` คือเสียงชัดเจน) เก็บเป็น `.m4a` `audio/mp4`, MP3 (`ID3` หรือ frame sync ที่ layer ไม่ใช่ 00) เป็น `.mp3` `audio/mpeg` และ AAC แบบ ADTS เป็น `.aac` `audio/aac` อย่างอื่นเป็น `failed` ชนิดของเสียงอ่านจาก 16 byte แรกก่อนเก็บ ไฟล์จึงได้นามสกุลและ `Content-Type` ที่ browser เล่นได้ ไม่ใช้ `Content-Type` ที่ LINE ส่งมา
- เสียงไม่เกิน `AUDIO_MAX_BYTES` เกินเป็น `too_large` ไม่มีภาพตัวอย่าง การรอไฟล์ที่ยังไม่พร้อม (202) งบเวลา `MEDIA_JOB_BUDGET_MS` และการคืนสภาพงานที่ค้างใช้กฎเดียวกับรูปและวิดีโอ (ดาวน์โหลดหนึ่งครั้งต่อรอบเหมือนรูป จึงอยู่ในอสมการของวิดีโอที่ `timing-budget.spec.ts` ตรึงไว้)
- ไฟล์เสียงเสิร์ฟทาง URL เดียวกับสื่ออื่นพร้อม `X-Content-Type-Options: nosniff` ที่เก็บแบบ local รองรับ `Range: bytes=` (206 และ `Content-Range` 416 เมื่อเกินขนาด) เพื่อให้ browser เลื่อนตำแหน่งเล่นได้ Vercel Blob รองรับเอง CSP `media-src` เดิม (`'self'`, `blob:`, host ของ Blob) พอแล้ว ไม่ได้เพิ่ม
- ล้มเหลว: `mediaStatus` เป็น `failed` พร้อมเหตุผล (`mediaFailure`) และฟองบอกเหตุผลนั้น: เนื้อไฟล์ไม่ใช่ชนิดที่รับ (`unsupported_type`), ไฟล์อยู่ที่ URL นอก LINE ซึ่งระบบไม่ดึง (`external_source`), ดาวน์โหลดหรือเก็บไม่สำเร็จ (`download_failed`) หรืองานถูกตัดก่อนเก็บเสร็จ (`interrupted`) ไฟล์ใหญ่เกินบอกเพดานของชนิดนั้น ข้อความอยู่ใน [ui-copy](ui-copy.md#คำแทนสื่อและข้อความชนิดอื่น) `inbox.media.problem.*` แถวที่บันทึกก่อนมีเหตุผลแสดง "โหลดรูปไม่สำเร็จ"
- ค้าง: งานดาวน์โหลดอยู่ใน `after()` ของ webhook ถ้า function ถูกตัด แถวจะค้างที่ `pending` (ภาพ skeleton ตลอด) ทุกครั้งที่โหลดข้อความของแชทนั้น (`GET /api/contacts/:id/messages` ซึ่งหน้าแชท poll อยู่) สื่อที่ `pending` นานกว่า `MEDIA_STUCK_AFTER_MS` นับจาก `createdAt` เป็น `failed` ด้วยคำสั่งเดียว ([data-model กฎของ repository ข้อ 13](../architecture/data-model.md#กฎของ-repository)) และ log `media.store.stuck_recovered` พร้อม `contactId` และจำนวน

## ส่งข้อความ

กฎการส่งเหมือนกันทั้งข้อความของแอดมินและของ AI ขั้นตอนอยู่ใน `deliverOutbound` ของ [use-cases](../architecture/use-cases.md#deliveroutbound)

1. ถ้า Contact มี reply token ที่ยังอยู่ในช่วงใช้ได้ (`REPLY_TOKEN_USABLE_MS` นับจากเวลาของ event) ใช้ reply ก่อน เพราะไม่กินโควตา push
2. ถ้าไม่มี token หรือ LINE ปฏิเสธ token ใช้ push พร้อม retry key "ปฏิเสธ token" คือ 400 ที่ `message` ตรงกับ `Invalid reply token` (ไม่สนตัวพิมพ์) เท่านั้น ซึ่งหมายถึงยังไม่มีอะไรถูกส่ง
3. ถ้า reply ล้มเหลวเพราะเครือข่ายหรือ 5xx ข้อความเป็น `failed` และไม่ push ต่อเอง เพราะไม่รู้ว่า reply ไปถึงลูกค้าหรือไม่ 400 อื่นของ reply (เช่น body ผิดรูป ซึ่ง LINE บอกด้วย `details[].property`) เป็น `line.reply_failed` และไม่ push ต่อเช่นกัน เพราะ payload เดียวกันจะถูกปฏิเสธอีกและกินโควตา push
4. Push ทุกครั้งแนบ `X-Line-Retry-Key` ซึ่งเป็นค่าเดิมของข้อความนั้นเสมอ และถือว่าสำเร็จเมื่อ LINE ตอบว่ารับคำขอนี้ไปแล้ว ค่าของ header คือ UUID ที่มีบิต version 5 และ variant ของ RFC 4122 ซึ่งได้จาก 16 byte แรกของ SHA-256 ของ id ข้อความ (`toLineRetryKey`) เพราะ LINE รับ UUID version 4 และ 5 แน่นอน แต่ยังไม่มีหลักฐานว่ารับ version 7 ซึ่งเป็นรูปแบบของ id ข้อความ ค่าจึงเหมือนเดิมทุกครั้งที่ลองใหม่และหลัง restart ([ADR 0023](../adr/0023-retry-key-v5-window-and-reply-400.md))
5. แอดมินกด "ส่งอีกครั้ง" แล้วระบบใช้ push ด้วย retry key เดิมเสมอ ไม่ใช้ reply token LINE จำ retry key ไว้ 24 ชั่วโมง หลังจากนั้น key เดิมถูกถือเป็นคำขอใหม่ ระบบจึงปฏิเสธ "ส่งอีกครั้ง" ด้วย `message.retry_expired` เมื่อผ่าน `LINE_RETRY_KEY_WINDOW_MS` นับจาก push ครั้งแรกของข้อความนั้น (`Message.firstPushAt`) ฟองแสดงเหตุผลและซ่อนปุ่ม แอดมินต้องพิมพ์ส่งใหม่ ข้อความที่ยังไม่เคย push (reply ล้มเหลว) ไม่มีหน้าต่างนี้
6. Retry อัตโนมัติภายใน adapter เฉพาะเครือข่ายล่ม, 5xx และ 429 ไม่เกิน `LINE_MAX_RETRIES` โดยเคารพเวลาที่ LINE กำหนดใน `Retry-After` เมื่อไม่มี `Retry-After` รอแบบเพิ่มเท่าตัวจาก `LINE_RETRY_BASE_DELAY_MS` และถ้า `Retry-After` ยาวกว่า `LINE_RETRY_AFTER_MAX_MS` adapter ไม่รอ แต่คืน error พร้อม `retryAfterSeconds` ทันที (ค่าอยู่ใน [project-setup](../architecture/project-setup.md#104-adapter-และ-route))
7. ข้อความที่ยาวเกิน `LINE_TEXT_MAX_CHARS` ถูกแบ่งเป็นหลายข้อความ

8. เมื่อ reply หรือ push สำเร็จ ระบบเก็บ `sentMessages[].id` ของคำตอบตามลำดับของข้อความใน `Message.lineSentIds` ของข้อความขาออกนั้น (ทั้งของแอดมินและ AI ทั้งตัวอักษร รูป และวิดีโอ) เพื่อให้รู้ว่าลูกค้าตอบกลับข้อความใด คำตอบที่ไม่มี `sentMessages` หรือ id ที่อ่านไม่ได้ไม่ทำให้การส่งล้ม (เก็บเท่าที่อ่านได้) push ที่ LINE ตอบ 409 ว่ารับ retry key ไปแล้วไม่มี id
9. `quoteToken` ของข้อความขาเข้าไม่ถูกเก็บ เพราะแอดมินยังอ้างถึงข้อความของลูกค้าตอนตอบไม่ได้ (งานที่อาจทำต่อ)

เหตุผลอยู่ใน [ADR 0010](../adr/0010-reply-token-first-and-idempotency.md)

## Rich menu

เมนูสามปุ่มใต้ช่องพิมพ์ของลูกค้า แอดมิน publish และนำออกได้จาก ตั้งค่า › Rich menu และข้อความต้อนรับ ([admin-backoffice](admin-backoffice.md#ส่วน-rich-menu-และข้อความต้อนรับ)) เหตุผลอยู่ใน [ADR 0027](../adr/0027-rich-menu-and-welcome-card.md)

### รูปและพื้นที่กด

- ขนาด compact 2500×843 แบ่งสามช่องกว้าง 833, 834 และ 833 px (`richMenuSpec` ใน `src/core/domain/rich-menu.logic.ts`) `selected: true` เมนูจึงเปิดอยู่ตอนลูกค้าเข้าแชท และ `chatBarText` คือ "เมนู"
- รูปมาจาก `scripts/brand/richmenu-3x1.html` (ฟอนต์ LINE Seed Sans TH ของ repo) เรนเดอร์ด้วย `pnpm exec tsx scripts/render-brand-assets.ts` เป็น `public/brand/richmenu-3x1.png` (ไม่เกิน 1 MB ตามข้อจำกัดของ LINE) และเป็น base64 ใน `src/adapters/line/rich-menu-image.generated.ts` ที่ adapter อัปโหลด เพราะไฟล์ใน `public/` ไม่อยู่ใน serverless function
- ทุกปุ่มเป็น postback action ที่มี `displayText` เป็นชื่อปุ่ม LINE จึงแสดงชื่อปุ่มในแชทของลูกค้าเหมือนลูกค้าพิมพ์เอง และ `data` มีรุ่นกำกับ `tw1:{action}` (`ai_on`, `admin`, `how_to`) data รุ่นอื่นหรือค่าที่ไม่รู้จักถูกเพิกเฉย ถ้าวันหนึ่งเปลี่ยนรูปแบบของ data ต้องใช้ prefix ใหม่

### Publish และนำออก

1. Publish (`PublishRichMenu`): สร้างเมนู (`POST /v2/bot/richmenu`) → อัปโหลดรูป PNG ที่ host ของ content (`POST https://api-data.line.me/v2/bot/richmenu/{id}/content`) → ตั้งเป็นเมนูเริ่มต้นของทุกคน (`POST /v2/bot/user/all/richmenu/{id}`) → บันทึก id และเวลาด้วย compare-and-set บน id ที่บันทึกไว้ก่อนเริ่ม แล้วลบเมนูที่ publish ไว้ก่อน (`DELETE /v2/bot/richmenu/{id}`) ถ้าการ publish อีกครั้งที่ทำพร้อมกันบันทึกก่อน รอบนี้ตั้งเมนูที่บันทึกนั้นเป็นค่าเริ่มต้นอีกครั้ง ลบเมนูของตัวเอง และตอบ `line.rich_menu_conflict` ที่ LINE จึงเหลือเมนูเดียวที่ตรงกับที่หน้าตั้งค่าแสดง
2. ขั้นใดล้ม ระบบลบเมนูที่เพิ่งสร้าง (ลบไม่ได้ก็ log `line.rich_menu.cleanup_failed`) เมนูเดิมยังเป็นเมนูเริ่มต้นเหมือนก่อนกด และบันทึกรหัสใน `Settings.richMenuError` ซึ่งหน้าตั้งค่าแสดงจนกว่าจะ publish หรือนำออกสำเร็จ ยกเว้นการตั้งเมนูเริ่มต้นที่ไม่ได้คำตอบ (`line.unavailable` หลัง timeout หรือ 5xx): LINE อาจตั้งเมนูใหม่ไปแล้ว ระบบจึงไม่ลบเมนูใหม่ (การลบเมนูที่เป็นค่าเริ่มต้นทำให้ลูกค้าไม่มีเมนู) แต่บันทึก id ของมันไว้ การ publish หรือนำออกครั้งถัดไปจึงลบมันได้ เมนูเดิมยังอยู่ที่ LINE และยังเป็นค่าเริ่มต้นถ้าการตั้งไม่ได้เกิด แต่ระบบไม่ติดตาม id ของมันอีก (การนำออกล้างเมนูเริ่มต้นของทุกคน จึงไม่เหลือผลกับลูกค้า)
3. สร้างเมนูและอัปโหลดรูปลองครั้งเดียว (ลองซ้ำหลังผลไม่แน่นอนอาจได้เมนูสองอันหรือรูปถูกปฏิเสธ) การตั้งเมนูเริ่มต้น การล้าง และการลบ retry ตามกฎของ adapter
4. นำออก (`RemoveRichMenu`): ล้างเมนูเริ่มต้นของทุกคน (`DELETE /v2/bot/user/all/richmenu`) แล้วลบเมนูที่บันทึกไว้ เมนูที่ LINE ไม่รู้จัก (404) ถือว่าลบแล้ว ล้มเมื่อใดเก็บ id เดิมไว้ให้กดใหม่ได้
5. 401 ของ LINE ตอบหน้าเว็บเป็น `line.credentials_invalid` และ 429 เป็น `line.unavailable` (สองรหัสนั้นไม่มี HTTP status ของตัวเอง) แต่ `richMenuError` เก็บรหัสเดิมของ LINE
6. อย่าตั้ง rich menu ใน LINE Official Account Manager อีกที่หนึ่ง เมนูที่ตั้งผ่าน API กับที่ตั้งใน Manager ทับกัน ([line-oa-setup](../runbooks/line-oa-setup.md#8-rich-menu-และข้อความต้อนรับ))

### เมื่อลูกค้ากดปุ่ม

`ReceiveLineEvents` เก็บการกดเป็นข้อความขาเข้าชนิด `text` ที่ข้อความคือชื่อปุ่ม (สิ่งที่ LINE แสดงในแชทของลูกค้า) และ `eventCode` เป็น `customer.tapped_ai_on`, `customer.tapped_admin` หรือ `customer.tapped_how_to` นับเป็นข้อความใหม่ของลูกค้า (ยังไม่อ่าน, ลำดับรายชื่อ, reply token) หน้าเว็บแสดงเป็นบรรทัดเหตุการณ์ "ลูกค้ากดปุ่ม …" ลูกค้าที่ยังไม่มีในระบบถูกสร้างพร้อมดึง profile เหมือนข้อความแรก แล้วงานหลังตอบ 200 (`HandleRichMenuAction`) ทำตามปุ่ม

| ปุ่ม | เงื่อนไข | ระบบทำอะไร |
| --- | --- | --- |
| คุยกับ AI | kill switch ปิด | ส่ง "ตอนนี้ AI ปิดให้บริการอยู่ แอดมินจะมาตอบแทนนะคะ" (หรือ "นะครับ") แชทรอแอดมินด้วย `ai_unavailable` AI ของลูกค้าคนนี้ไม่เปลี่ยน |
| คุยกับ AI | งบของวันนี้เต็ม | ส่ง "วันนี้ AI ให้บริการครบโควตาแล้ว แอดมินจะมาตอบแทนนะคะ" แชทรอแอดมินด้วย `budget_reached` |
| คุยกับ AI | อื่น ๆ (รวมเมื่อเปิดอยู่แล้ว) | เปิด AI ของลูกค้าคนนี้ ล้างสถานะรอแอดมิน แล้วส่งต่อให้ `GenerateAiReply` ในงานเดียวกัน ซึ่งตรวจ kill switch, งบ, lock, ขอบเขตหัวข้อ และบันทึกค่าใช้จ่ายตามปกติ โมเดลเห็นการกดเป็นบรรทัดเริ่มคุยและทักทายตามกฎการทักทาย ([ai-prompt ข้อ 4.2](ai-prompt.md#42-แปลงเป็น-turn)) |
| คุยกับแอดมิน | เสมอ | ปิด AI ของลูกค้าคนนี้ แชทรอแอดมินด้วย `customer_asked_admin` (บรรทัดเหตุการณ์ครั้งเดียวแม้กดซ้ำ) และส่ง "รับทราบ แอดมินจะมาตอบแชทนี้นะคะ" |
| วิธีทดสอบ | เสมอ | ส่งข้อความวิธีทดสอบที่บันทึกไว้ หรือข้อความเริ่มต้นเมื่อว่าง |

- การกด "คุยกับแอดมิน" และ "วิธีทดสอบ" ไม่เริ่ม AI จึงไม่แทนข้อความของลูกค้าที่ AI ยังไม่ได้ตอบ: ข้อความที่ส่งก่อนการกด "วิธีทดสอบ" ในช่วงรวมข้อความยังถูก AI ตอบครั้งเดียว (หลังข้อความวิธีทดสอบ) และข้อความก่อนการกด "คุยกับแอดมิน" ไม่ถูก AI ตอบเพราะการกดปิด AI ส่วน "คุยกับ AI" ที่มาพร้อมข้อความ (ก้อนเดียวกันหรือก่อนงานของการกดเปิด AI) ทำให้ข้อความนั้นถูกตอบครั้งเดียว ([use-cases HandleRichMenuAction](../architecture/use-cases.md#handlerichmenuaction))
- ข้อความคงที่ไม่เรียกโมเดล ส่งเป็นข้อความขาออกผู้ส่ง `ai` ตามกฎ "ส่งข้อความ" (reply token ของการกดก่อน แล้วจึง push) ส่งไม่สำเร็จเป็น `failed` ที่แอดมินกด "ส่งอีกครั้ง" ได้ คำลงท้ายตาม `aiPoliteParticle` โดย "ค่ะ" หลัง "นะ" เขียน "คะ" เหมือน `handoffText`
- ข้อความวิธีทดสอบเริ่มต้น (บรรทัดแรกลงท้ายตามคำลงท้ายที่ตั้ง):

  ```
  ลองได้ตามนี้เลยค่ะ
  1. กด "คุยกับ AI" แล้วพิมพ์ถามอะไรก็ได้ AI จะตอบและแนะนำตัวในครั้งแรก
  2. ส่งรูป สติกเกอร์ หรือวิดีโอ AI จะหยุดและส่งต่อให้แอดมิน
  3. กด "คุยกับแอดมิน" AI จะปิด และแอดมินจะมาตอบเอง
  4. กดค้างที่ข้อความแล้วเลือก "ตอบกลับ" แอดมินจะเห็นว่าคุณอ้างถึงข้อความไหน
  ข้อความทั้งหมดไปขึ้นที่หน้า webchat ของแอดมินทันที
  ```

- กดถี่: เกิน `RATE_LIMIT_RICH_MENU_TAP` ต่อลูกค้า การกดนั้นถูกทิ้ง (ไม่บันทึก ไม่ตอบ) พร้อม log `line.postback.rate_limited` event ที่ส่งซ้ำถูกกันด้วย `webhookEventId` เหมือน event อื่น
- Log มีแค่ `contactId` และชื่อปุ่ม (`reason`) ไม่มี postback data หรือข้อความ

## ข้อความต้อนรับ

เมื่อมี follow event (เพิ่มเพื่อนครั้งแรก หรือเลิกบล็อก) ที่มี reply token ระบบส่งการ์ดต้อนรับหนึ่งครั้งด้วย reply token ของ event นั้น (`SendWelcome` หลังตอบ 200) เหตุผลอยู่ใน [ADR 0027](../adr/0027-rich-menu-and-welcome-card.md)

- การ์ดเป็น Flex bubble: หัวพื้น gradient (`background.type: linearGradient` 135deg ส้มไปชมพูบานเย็น และ `backgroundColor` สี accent สำรอง) รูปโลโก้จาก `{APP_BASE_URL}/brand/app-icon-512.png` เมื่อ `APP_BASE_URL` เป็น HTTPS เท่านั้น (ไม่ใช่ HTTPS เช่น Docker ในเครื่อง หัวมีตัว "T" แทนรูป) บรรทัด "ยินดีต้อนรับสู่" กับชื่อ LINE OA (`Settings.lineBotName` หรือ "Test webchat" เมื่อไม่มี) ข้อความต้อนรับ บรรทัดหมายเหตุสีจาง "ข้อความของคุณจะขึ้นที่หน้า webchat ของแอดมินทันที" และสามปุ่ม: "คุยกับ AI" (primary), "คุยกับแอดมิน" (secondary), "วิธีทดสอบ" (link) ซึ่งใช้ postback data และตัวจัดการเดียวกับ rich menu
- `altText` คงที่และเป็นกลาง: "ยินดีต้อนรับ กดปุ่มในข้อความเพื่อเริ่มคุยกับ AI หรือแอดมิน" ข้อความต้อนรับเริ่มต้น "ขอบคุณที่เพิ่มเพื่อนนะคะ ที่นี่ทดลองคุยกับ AI และแอดมินได้เลยค่ะ" ลงท้ายตามคำลงท้ายที่ตั้ง ไม่มีชื่อ AI แอดมินแก้ได้ไม่เกิน `WELCOME_TEXT_MAX_CHARS`
- ส่งด้วย reply เท่านั้น ไม่ push ไม่เรียกโมเดล ส่งได้แม้ AI ปิด ไม่เปลี่ยนสวิตช์ AI และไม่นับเป็นข้อความของแอดมิน ส่งไม่สำเร็จ (token หมดอายุ, LINE ปฏิเสธ, ไม่มี credential) มีแค่ log `line.welcome.failed` ไม่มีอย่างอื่น
- ส่งสำเร็จแล้วเก็บเป็นข้อความขาออกผู้ส่ง `ai` ชนิด `text` (ข้อความคือเนื้อการ์ด) ที่ `eventCode` เป็น `welcome.sent` หน้าเว็บแสดงเป็นกล่อง "ข้อความต้อนรับ" ไม่เปลี่ยนตัวอย่างข้อความ ลำดับ หรือจำนวนยังไม่อ่านของรายชื่อ
- Follow ที่ LINE ส่งซ้ำ (`isRedelivery`) ไม่มี reply token และ `webhookEventId` เดิมถูกข้าม การ์ดจึงไม่ถูกส่งซ้ำ
- ปิดได้ที่สวิตช์ "ส่งข้อความต้อนรับเมื่อเพิ่มเพื่อน" (ค่าเริ่มต้นของการติดตั้งใหม่คือเปิด) และต้องปิด "Greeting message" ใน LINE Official Account Manager ไม่อย่างนั้นลูกค้าได้สองข้อความ ([line-oa-setup](../runbooks/line-oa-setup.md#8-rich-menu-และข้อความต้อนรับ))
- ขนาดของ bubble ต่ำกว่าเพดาน 30 KB ของ LINE มาก (ข้อความต้อนรับไม่เกิน 300 ตัวอักษร) ป้ายปุ่มไม่เกิน 20 ตัวอักษร

### ต้องยืนยันกับ LINE จริง

- Flex `linearGradient` แสดงบน iOS, Android และ LINE บน desktop หัวของการ์ดตั้ง `backgroundColor` เป็นสี accent ทึบไว้ด้วย แอปที่ไม่รองรับ gradient จึงควรเห็นพื้นสีชมพูบานเย็นแทน (ต้องดูด้วยตา)
- รูปโลโก้โหลดได้จาก URL ของ production (HTTPS, ไม่ผ่าน cookie gate)
- Rich menu 2500×843 ที่ `selected: true` แสดงเปิดอยู่ และ `displayText` ขึ้นเป็นข้อความของลูกค้า
- Postback ของปุ่มใน Flex มี reply token ใช้ได้ และไม่มี `displayText` ซ้ำเมื่อกดเร็ว
- `DELETE /v2/bot/user/all/richmenu` เมื่อไม่มีเมนูเริ่มต้นตอบ 2xx หรือ 404 และอัปโหลดรูปซ้ำในเมนูเดิมถูกปฏิเสธ

## ข้อความที่ตอบกลับ

- ข้อความตัวอักษรขาเข้าที่มี `message.quotedMessageId` (string ไม่ว่าง ค่าอื่นถูกเพิกเฉยโดยไม่ทิ้งข้อความ) เก็บ id นั้นไว้ การหาข้อความต้นทางทำตอนอ่าน ไม่ใช่ตอนรับ: `GetMessages` รวม id ที่ถูกอ้างของทั้งหน้าแล้วหาด้วย `findByLineIds` ครั้งเดียว (`lineMessageId` ของข้อความขาเข้า หรือหนึ่งใน `lineSentIds` ของข้อความขาออก ในแชทเดียวกัน) ทั้งโหลดล่าสุด โหลดย้อนหลัง และ polling ([use-cases](../architecture/use-cases.md#getmessages))
- ข้อความต้นทางที่หาไม่พบ (ส่งก่อน migration ที่เจ็ด, เป็นของแชทอื่น หรือไม่เคยถูกเก็บ) แสดงเป็น "ข้อความต้นทางไม่พร้อมแสดง"
- ประวัติที่ส่งให้โมเดลมีบรรทัดสั้นบอกว่าลูกค้าตอบกลับข้อความใด ([ai-prompt ข้อ 4.2](ai-prompt.md#42-แปลงเป็น-turn))
- ต้องยืนยันกับ LINE จริง: ชื่อและรูปแบบของ `quotedMessageId` (สมมติเป็น string id ของข้อความ), ข้อความชนิดใดมี `quotedMessageId` (ระบบอ่านเฉพาะข้อความตัวอักษร), และ `sentMessages[].id` ของ reply และ push เป็น id เดียวกับที่ `quotedMessageId` อ้าง (ขั้นใน [line-oa-setup](../runbooks/line-oa-setup.md#ทดสอบด้วยมือเมื่อมี-line-oa-จริง))

### งานส่งที่ค้าง

ข้อความขาออกเป็น `pending` ระหว่างส่ง ถ้า function ที่ส่ง (คำขอของแอดมิน หรือ `after()` ของ webhook สำหรับ AI) ถูกตัดก่อนรู้ผล แถวจะค้าง "กำลังส่ง" และกด "ส่งอีกครั้ง" ไม่ได้ ทุกครั้งที่โหลดข้อความของแชทนั้น ข้อความที่ `pending` นานกว่า `SEND_STUCK_AFTER_MS` นับจากเวลาที่การส่งรอบนั้นเริ่ม (`createdAt` หรือเวลาที่กด "ส่งอีกครั้ง" ล่าสุด) เป็น `failed` ด้วยรหัส `line.send_interrupted` ด้วยคำสั่งเดียว และ log `line.send.stuck_recovered` พร้อม `contactId` และจำนวน แอดมินจึงกด "ส่งอีกครั้ง" ได้ ซึ่ง push ด้วย retry key เดิมตามข้อ 5 ถ้าการส่งครั้งที่ถูกตัดถึงลูกค้าแล้ว LINE ควรไม่ส่งซ้ำเพราะ key เดิม (ต้องยืนยันตาม [line-oa-setup](../runbooks/line-oa-setup.md#ทดสอบด้วยมือเมื่อมี-line-oa-จริง)) `SEND_STUCK_AFTER_MS` มากกว่าเวลาแย่ที่สุดของการส่งและเพดานเวลาของ function จึงไม่ตัดการส่งที่ยังทำอยู่

## สื่อขาออก

| | รูป | วิดีโอ |
| --- | --- | --- |
| ชนิด | JPEG, PNG | MP4 |
| ขนาดสูงสุด | `IMAGE_MAX_BYTES` | `VIDEO_MAX_BYTES` |
| ภาพตัวอย่าง | ย่อรูปใน browser | จับเฟรมแรกใน browser |

- Browser อัปโหลดตรงเข้าที่เก็บไฟล์ด้วยสิทธิ์จาก `POST /api/uploads` ซึ่งกำหนดชนิดและขนาดที่แน่นอนของไฟล์ ที่เก็บแบบ local (Docker) รับ PUT ที่ยาวเท่าขนาดนั้นพอดี body ที่สั้นกว่า (ถูกตัดระหว่างทาง) ถูกปฏิเสธด้วย `upload.incomplete` แทนการส่งไฟล์ที่เสียให้ลูกค้า และ PUT ไปที่ path บน origin ที่ browser เปิดอยู่ (ไม่ใช่ `APP_BASE_URL`) Vercel Blob รับไม่เกินขนาดนั้น
- ก่อนเลือกไฟล์ ปุ่มแนบบอกชนิดที่รับและเพดานของรูปและวิดีโอ และทุกข้อความผิดพลาดเรื่องชนิดหรือขนาดบอกสิ่งที่รับได้และขนาดของไฟล์ที่เลือก ([ui-screens ข้อ 5.10](ui-screens.md#510-ไฟล์แนบ-attachmenttray))
- รูป WebP ถูกแปลงเป็น JPEG ใน browser ด้วย canvas
- รูป HEIC และ HEIF ต้องใช้ได้ใน Chrome และ Firefox: browser ลองถอดรหัสเองก่อน ถ้าไม่ได้จึงโหลด `heic-to` ด้วย `import()` แบบ dynamic เฉพาะตอนที่เลือกไฟล์ HEIC (ไม่อยู่ใน bundle แรก) แปลงเป็น JPEG แล้วทำขั้นตอนภาพตัวอย่างและอัปโหลดตามปกติ ถ้าแปลงไม่สำเร็จ แสดงข้อความให้ใช้ไฟล์ JPEG หรือ PNG ([ADR 0019](../adr/0019-heic-conversion-with-heic-to.md), [ui-screens](ui-screens.md#76-ขั้นตอนแนบไฟล์))
- Server รับเฉพาะ JPEG, PNG และ MP4 การแปลงทั้งหมดจึงเกิดใน browser ก่อนขอสิทธิ์อัปโหลด
- วิดีโอ MOV ถูกปฏิเสธ พร้อมข้อความให้ใช้ MP4
- LINE ต้องการ URL แบบ HTTPS ที่เปิดสาธารณะ ชื่อไฟล์จึงเป็นค่าสุ่มที่เดาไม่ได้
- ไฟล์ที่อัปโหลดแล้วแต่กดยกเลิกถูกลบ ส่วนกรณีปิดแท็บกลางคันไม่ตามเก็บ

## Loading ฝั่ง LINE

ระบบเรียก API แสดง loading ในแอป LINE ของลูกค้าเป็นเวลา `LINE_LOADING_SECONDS` (ต้องยืนยันช่วงที่ LINE รับ) ในสองกรณี: ระหว่างที่ AI กำลังตอบ และเมื่อแอดมินพิมพ์ในช่องตอบ ซึ่งหน้าเว็บส่งไม่เกินหนึ่งครั้งต่อ `TYPING_PING_INTERVAL_MS` และ server จำกัดไม่เกิน `RATE_LIMIT_TYPING` ต่อลูกค้า ถ้าเรียกไม่สำเร็จ ไม่ถือเป็นความล้มเหลว

## กรณีผิดพลาด

| เหตุการณ์ | ระบบทำอะไร | แอดมินเห็นอะไร |
| --- | --- | --- |
| Access token ผิดหรือหมดอายุ | ข้อความเป็น `failed` และบันทึก `lastLineError` | "ส่งไม่สำเร็จ" และสถานะระบบแจ้งให้ตรวจ credential |
| ลูกค้าเลิกติดตาม | ไม่เรียก LINE | ช่องตอบถูกปิด |
| โควตา push เต็ม | ข้อความเป็น `failed` แผนฟรีส่ง push ได้ราว 300 ข้อความต่อเดือน reply ไม่นับ แต่ทุก push ที่ใช้แทน reply (token หมดอายุ, ข้อความของ AI ที่ตอบช้า, ข้อความของแอดมินที่ไม่มี token) และทุก "ส่งอีกครั้ง" นับในโควตา ([line-oa-setup](../runbooks/line-oa-setup.md#โควตา-push)) | "ส่งไม่สำเร็จ โควตาข้อความของ LINE เต็ม" |
| LINE ดึง URL ของสื่อไม่ได้ | ข้อความเป็น `failed` | "ส่งไม่สำเร็จ" และกดส่งอีกครั้งได้โดยไม่ต้องอัปโหลดใหม่ |
| Function ถูกตัดระหว่างส่ง | หลัง `SEND_STUCK_AFTER_MS` ข้อความเป็น `failed` ด้วย `line.send_interrupted` | "ส่งไม่สำเร็จ ระบบหยุดทำงานก่อนรู้ผลการส่ง กด "ส่งอีกครั้ง"" |
| Reply ถูกปฏิเสธด้วย 400 ที่ไม่ใช่เรื่อง token | ข้อความเป็น `failed` ด้วย `line.reply_failed` ไม่ push ต่อ | "ส่งไม่สำเร็จ LINE ไม่รับข้อความนี้ กด "ส่งอีกครั้ง"" |
| กด "ส่งอีกครั้ง" หลังผ่าน `LINE_RETRY_KEY_WINDOW_MS` นับจาก push ครั้งแรก | ไม่เรียก LINE ตอบ 409 `message.retry_expired` | ฟองแสดง "ส่งไม่สำเร็จ · ส่งอีกครั้งไม่ได้แล้วเพราะเกิน 24 ชั่วโมงหลังส่งครั้งแรก พิมพ์ข้อความแล้วส่งใหม่" และไม่มีปุ่ม |
| LINE ยังเตรียมสื่อขาเข้าไม่เสร็จจนหมดงบของงาน | สื่อเป็น `failed` ด้วย `line.content_not_ready` | "โหลดรูปไม่สำเร็จ" หรือ "โหลดวิดีโอไม่สำเร็จ" |
| ฐานข้อมูลล่มจนบันทึก event ใดในก้อนไม่ได้ | webhook ตอบ 503 ให้ LINE ส่งซ้ำ | ไม่มี ข้อความขึ้นเมื่อ LINE ส่งซ้ำ |
| Function ถูกตัดระหว่างดาวน์โหลดสื่อขาเข้า | หลัง `MEDIA_STUCK_AFTER_MS` สื่อเป็น `failed` | "โหลดรูปไม่สำเร็จ" หรือ "โหลดวิดีโอไม่สำเร็จ" |

## ข้อจำกัดที่รู้

- LINE ไม่ส่งสถานะการอ่านให้ระบบภายนอก จึงไม่แสดง "อ่านแล้ว"
- รองรับ LINE OA เดียว

## สิ่งที่ต้องยืนยันจากเอกสาร LINE ก่อนสร้าง

อายุของ reply token, ขีดจำกัดขนาดและชนิดของรูปกับวิดีโอ, ขีดจำกัดความยาวข้อความ, ระยะเวลาที่ LINE เก็บไฟล์ และเงื่อนไขของ API แสดง loading ส่วนที่ยืนยันจากเอกสารอย่างเดียวไม่ได้ต้องทดสอบด้วยมือกับ LINE OA จริงตามรายการใน [line-oa-setup](../runbooks/line-oa-setup.md#ทดสอบด้วยมือเมื่อมี-line-oa-จริง) และติดตามใน [implementation-plan](../plans/implementation-plan.md#สิ่งที่ต้องยืนยันก่อนหรือระหว่างสร้าง)

## วิธีทดสอบ

- Unit: การตรวจ signature, การกันซ้ำ, การเลือก reply หรือ push, การแบ่งข้อความยาว, การคืนสภาพสื่อและการส่งที่ค้าง (`get-messages.use-case.spec.ts` และชุดทดสอบของ `MessageRepository` ทั้งตัวปลอมและ Postgres), การรอสื่อที่ยังไม่พร้อม, หน้าต่างของ retry key, 503 ของก้อนที่บันทึกไม่ได้และการส่งซ้ำที่บันทึกครั้งเดียว
- Adapter: รูปแบบ request ที่ส่งไป stub (header, retry key แบบ version 5, body), การแยก 400 ของ reply, 202 ของ content และการตรวจ Channel secret
- Fixture: payload ตัวอย่างของทุกชนิด event รวม `postback.json`
- Rich menu และข้อความต้อนรับ: unit ทุกเงื่อนไขของปุ่มและการ publish (`rich-menu.use-case.spec.ts`), adapter (รูปแบบ request ของ rich menu, การอัปโหลดรูปที่ host ของ content, Flex bubble), ชุดทดสอบของ port ทั้งตัวปลอมและ stub และ E2E เส้นที่ 14 และ 15
- E2E เส้นที่ 1, 2, 5 และ 7 ใน [test-strategy](../qa/test-strategy.md)

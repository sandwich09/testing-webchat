## 2. ทดสอบอย่างไร

เราแบ่ง test เป็นสี่ชั้น แต่ละชั้นตอบคำถามคนละข้อ

| ชั้น         | ตอบคำถามว่า                                           | รันกับอะไร                                                        | เวลาโดยประมาณ |
| ------------ | ----------------------------------------------------- | ----------------------------------------------------------------- | ------------- |
| Unit         | logic ของแต่ละส่วนถูกไหม                              | fake ในหน่วยความจำ ไม่แตะ network หรือ database                   | 10 วินาที     |
| Adapter      | โค้ดที่คุยกับของจริงทำงานถูกไหม                       | PostgreSQL จริงใน Docker และ stub ของ LINE กับ Claude             | 40 วินาที     |
| E2E          | ผู้ใช้ทำงานจนจบได้จริงไหม                             | แอปที่ build แบบ production ใน Docker เปิดด้วย browser จริง        | 2 นาที        |
| ทดสอบด้วยมือ | ต่อกับ LINE และ Claude ตัวจริงแล้วยังใช้ได้ไหม        | production บน Vercel                                              | 20 นาที       |

เรื่องที่ควรรู้ก่อนอ่านผล

- **CI ไม่เรียก LINE และ Claude ตัวจริง** เพราะทั้งคู่มีค่าใช้จ่ายและผลไม่นิ่งพอจะใช้ตัดสินว่า build ผ่านหรือไม่ เราเขียน stub ที่ตอบตามรูปแบบของ API จริง รวมถึงกรณี error เช่น reply token หมดอายุ rate limit และ timeout
- **Repository ทุกตัวมี test ชุดเดียวที่รันสองรอบ** รอบหนึ่งกับ fake อีกรอบกับ PostgreSQL จริง fake กับของจริงจึงทำงานเหมือนกันเสมอ ถ้าไม่เหมือน test จะ fail
- **E2E ทุกข้อรันสองขนาดจอ** คือ 1280 px และ 390 px และ fail ทันทีถ้ามี console error หรือ CSP violation แม้หน้าจอจะดูปกติ
- **Test ไม่ผูกกับวันที่จริง** เวลาในระบบมาจาก clock ที่ test กำหนดเอง ผลจึงไม่เปลี่ยนตามวันที่รัน

นอกจาก test แล้ว CI ยังตรวจอีกห้าอย่างทุกรอบ

| ขั้น                      | กันปัญหาอะไร                                                        |
| ------------------------- | ------------------------------------------------------------------- |
| `migrations:immutable`    | มีคนแก้ migration ที่ apply ไปแล้ว                                  |
| `migrations:destructive`  | migration ที่ลบหรือเปลี่ยนชนิดคอลัมน์โดยไม่ได้อนุมัติ               |
| `docs:check`              | เอกสารอ้างถึงไฟล์หรือหัวข้อที่ไม่มีอยู่                             |
| `pnpm audit`              | dependency ที่มีช่องโหว่ระดับ high ขึ้นไป                           |
| gitleaks                  | secret หลุดเข้า Git history                                         |

ชุดนี้เรียก Claude จริงและมีค่าใช้จ่าย จึงไม่อยู่ใน CI ปกติ แต่มี workflow แยกชื่อ `ai-eval` ที่ต้องกดสั่งเองและติ๊ก `confirm` ทุกครั้ง workflow ตรวจก่อนว่า API key ยังใช้ได้ แล้วรันชุดคำถามกับทุกโมเดลที่หน้าตั้งค่าให้เลือก ([ADR 0032](../adr/0032-manual-ai-eval-workflow.md))

ยังไม่ได้รัน เมื่อรันแล้วจะใส่ผลของแต่ละโมเดลตรงนี้: อัตราที่ตอบถูก อัตราที่ injection สำเร็จ อัตราที่ขอบเขตหัวข้อกันผิด และค่าใช้จ่ายจริง

## 7. สิ่งที่ยังไม่ได้ทดสอบ

- **Browser อื่น** ทดสอบเฉพาะ Chromium ยังไม่ได้ลอง Firefox และ Safari
- **มือถือจริง** จอ 390 px ทดสอบด้วยการจำลองใน Chromium ไม่ใช่เครื่องจริง รวมถึงรูป HEIC จาก iPhone จริง
- **Load** ไม่มี load test ระบบออกแบบสำหรับแอดมินไม่กี่คนกับผู้ใช้หลักร้อย
- **ดึงโปรไฟล์ใหม่วันละครั้ง** ไม่มี E2E เพราะต้องรอข้อมูลเก่าเกิน 24 ชั่วโมง มี unit test และ test กับ PostgreSQL จริง
- **Function ที่รันนาน** เพดาน 300 วินาทีของ Vercel ยังไม่เคยถูกทดสอบด้วยงานที่ใช้เวลานานจริง เช่น PDF ขนาดใหญ่
- **อ้างอิงบับเบิลที่เกิดจากการกดปุ่ม** เมื่อผู้ใช้กดปุ่มใน rich menu หรือการ์ด LINE แสดงบับเบิลข้อความฝั่งผู้ใช้ แต่ส่งมาให้ระบบเป็น postback ที่ไม่มี message ID ถ้าผู้ใช้ตอบกลับโดยอ้างอิงบับเบิลนั้น webchat จะขึ้นว่า "ข้อความต้นทางไม่พร้อมแสดง" (ตรวจจากข้อมูลบน production แล้ว)
- **LINE ล่มหรือช้าของจริง** ทดสอบเฉพาะกับ stub ที่จำลอง timeout และ error

## 8. รัน test เอง

```bash
pnpm install
pnpm test                 # unit
docker compose up -d --build --wait db stub app
docker compose run --rm seed
pnpm test:adapters        # adapter กับ PostgreSQL จริง
pnpm exec playwright install chromium   # ครั้งแรกเท่านั้น
pnpm test:e2e             # E2E
```

รายงาน E2E แบบ HTML และ coverage ของแต่ละรอบดาวน์โหลดได้จากหน้า Actions ของรอบนั้น ในส่วน Artifacts

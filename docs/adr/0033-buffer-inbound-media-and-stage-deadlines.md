# 0033: อ่านสื่อขาเข้าเข้าหน่วยความจำก่อนอัปโหลด และกำหนดเวลาทุกขั้น

> สถานะ: อนุมัติ · วันที่: 2026-11-19 · เสริม [0009](0009-media-in-vercel-blob.md)

## บริบท

บน production รูปที่ส่งจาก LINE ค้าง "กำลังโหลดรูป" ตลอด หลักฐานที่มี:

- webhook ตอบ 200 ใน 461 ms แล้วอีก 5 นาทีพอดี Vercel บันทึก `Task timed out after 300 seconds` งาน `store_media` ใน `after()` จึงค้างจน function ถูกตัด ไม่มี log `media.store.*` สักบรรทัด และแถวยัง `mediaStatus = pending`
- ข้อความเสียง 4 วินาที (ไฟล์เล็ก) ผ่านงานเดียวกันบน deployment เดียวกันได้ปกติ รูปจากมือถือ (หลายร้อย kB ถึงไม่กี่ MB) ค้าง
- ทางเดิมส่ง body ของ LINE แบบ stream ต่อเข้า `put()` ของ `@vercel/blob` เป็น `ReadableStream` ที่ไม่รู้ความยาว ทางนี้ไม่เคยรันกับ Blob จริง test ใช้ที่เก็บแบบ local ตัวปลอม หรือ stub

สิ่งที่พิสูจน์แล้ว: งานค้างโดยไม่มีขั้นใดจบหรือ error และไม่มีเพดานเวลาของงานที่ตัดได้ก่อน function สิ่งที่ยังเป็นข้อสันนิษฐาน: การเรียกใดค้างจริง ระหว่างการอ่าน body ของ LINE กับการอัปโหลดแบบ stream ของ Blob ข้อสังเกตจาก `@vercel/blob` 2.9.0 ใน `node_modules`: body ที่เป็น stream ถูกส่งด้วย `duplex: "half"` โดยไม่มีความยาว (ส่ง `x-content-length` เฉพาะเมื่อมี `onUploadProgress` หรือตั้ง `VERCEL_BLOB_USE_X_CONTENT_LENGTH`) และ SDK ลองใหม่เองได้ถึง 10 ครั้ง (`VERCEL_BLOB_RETRIES`) ซึ่ง stream ที่อ่านไปแล้วส่งซ้ำไม่ได้ ส่วน timeout ของ LINE ใช้ `AbortSignal.timeout` ของคำขอ ซึ่งการตัด body หลังได้ header แล้วขึ้นกับ fetch ที่ใช้ ไม่มีโค้ดของแอปตัดเอง

## การตัดสินใจ

1. Adapter ของ Vercel Blob อ่าน body ทั้งไฟล์เข้าหน่วยความจำก่อน แล้วเรียก `put()` ครั้งเดียวด้วย `Buffer` ที่รู้ความยาว ไม่ส่ง stream ต่อ stream อีก ระหว่างอ่านตรวจ `maxSizeBytes` ทีละ chunk เกินแล้วหยุดอ่าน ยกเลิก stream ต้นทาง และคืน `media.too_large` โดยไม่อัปโหลดอะไร stream ต้นทางที่ error คืน `storage.unavailable` โดยไม่อัปโหลดเช่นกัน ไม่ใช้ `multipart` เพราะ SDK อธิบายว่าเป็นทางของไฟล์ใหญ่ที่แบ่งส่วนส่งขนานกัน และไฟล์ขาเข้าไม่เกิน 50 MB สัญญาของ port `FileStorage.put` ไม่เปลี่ยน ชุดทดสอบของ port เพิ่มข้อ "body ขาดกลางทางแล้วไม่สำเร็จและไม่เหลือไฟล์" ซึ่งตัวปลอม ดิสก์ในเครื่อง และ Blob ผ่านเหมือนกัน
2. ทุกการเรียกภายนอกของงานมีเพดานของตัวเอง:
   - body ของ LINE: adapter ตัด body เองเมื่อ `LINE_CONTENT_TIMEOUT_MS` ของรอบนั้นหมด (ใช้ signal ของรอบนั้น และถือ reference ไว้จน body จบ) และเมื่อไม่มี chunk ใหม่นาน `LINE_CONTENT_IDLE_TIMEOUT_MS` ขณะรออ่าน (error `LineContentTimeoutError` ที่ไม่มีรหัส `media.too_large` จึงเป็น `failed`) เวลาแย่ที่สุดของการดาวน์โหลดหนึ่งครั้งจึงยังเป็น 100 วินาทีตามเดิม
   - Blob: `put` ทั้งการเรียกรวมการลองใหม่ของ SDK ไม่เกิน `STORAGE_PUT_TIMEOUT_MS`, `inspect` (`head` และการอ่าน 16 byte แรก) และ `delete` ไม่เกิน `STORAGE_CALL_TIMEOUT_MS` ทุกการเรียกส่ง `abortSignal` (SDK รับใน `BlobCommandOptions`) และ adapter คืนผลเมื่อครบเวลาแม้การเรียกไม่สนใจ signal
   - ทั้งงาน: `StoreInboundMedia` แข่งงานกับตัวจับเวลา `MEDIA_JOB_BUDGET_MS` นับจากเริ่มงาน (port `Clock.startTimer`) ถ้าครบก่อน ข้อความเป็น `failed` ด้วย `interrupted` (ค่าเดิมของ enum ไม่มี migration) พร้อม log ว่าค้างที่ขั้นใด ปล่อย stream ของ LINE และสิ่งที่ขั้นที่ถูกทิ้งทำทีหลังเปลี่ยนข้อความไม่ได้ เพราะทุกการเขียนเป็น compare-and-set บน `pending`
   - งานเริ่มขั้นถัดไปเฉพาะเมื่องบยังพอ: การรอไฟล์ที่ยังไม่พร้อมสำรอง `MEDIA_CONTENT_CALL_WORST_MS` + `MEDIA_STORE_CALL_WORST_MS` (ดาวน์โหลด original อีกครั้งและเก็บ) และภาพตัวอย่างของวิดีโอดึงเฉพาะเมื่องบที่เหลือยังพอสำหรับการดาวน์โหลดและการเก็บอีกหนึ่งชุด ไม่พอใช้ภาพจากวิดีโอเองตามกฎเดิม
3. งานบอกขั้นใน log: `media.store.started`, `media.store.downloaded` (`sizeBytes` ที่อ่านจาก LINE), `media.store.uploaded` (`sizeBytes` ที่เก็บ), `media.store.succeeded` (`durationMs`) และ `media.store.failed` ที่มี `stage` กับ `durationMs` field `stage` เพิ่มใน `LogFields` ค่ามาจาก `MediaStoreStage` ของแกนกลางเท่านั้น ไม่มี URL หรือ token

เหตุที่การเก็บทั้งไฟล์ในหน่วยความจำรับได้: เพดานคือรูป 10 MB เสียง 20 MB และวิดีโอ 50 MB ระหว่างต่อ chunk เป็นก้อนเดียวใช้ราวสองเท่าของไฟล์ชั่วครู่ (วิดีโอใหญ่สุดราว 100 MB) ซึ่งเล็กเมื่อเทียบกับหน่วยความจำเริ่มต้นของ function บน Vercel (2 GB ตามเอกสารของ Vercel ยังไม่ได้ตรวจในหน้าตั้งค่าของ project นี้ และ project ไม่ได้ตั้ง `memory` เอง)

## ทางเลือกที่พิจารณา

- ส่ง stream ต่อแต่ใส่ `x-content-length` หรือ `onUploadProgress`: ยังพึ่งทาง stream ที่ยังไม่รู้ว่าทำไมค้าง และการลองใหม่ของ SDK ส่ง stream ที่อ่านแล้วซ้ำไม่ได้
- `multipart: true`: SDK แบ่งส่วนและลองใหม่ทีละส่วนได้ แต่เรียกหลายครั้งต่อไฟล์ และไม่จำเป็นกับไฟล์ไม่เกิน 50 MB
- เพิ่มเฉพาะเพดานเวลาของทั้งงานโดยไม่แก้ทางอัปโหลด: ข้อความไม่ค้างแล้ว แต่รูปจริงจะ `failed` ทุกครั้งถ้าทาง stream ค้างจริง
- ให้ browser ดาวน์โหลดจาก LINE เอง: ต้องเปิด token ของ LINE ให้ browser และไฟล์ของ LINE หมดอายุ

## ผลที่ตามมา

- ไฟล์ที่ไม่ครบหรือใหญ่เกินไม่ถูกส่งไป Blob เลย จึงไม่มีไฟล์ครึ่งเดียวต้องลบ การอัปโหลดที่หมดเวลาอาจยังถูกเก็บที่ Blob ทีหลัง แต่ข้อความไม่ชี้ไฟล์นั้น จึงเปิดไม่ถึง (เหมือนไฟล์ที่ลบไม่สำเร็จแบบ best effort)
- ข้อจำกัด: หน่วยความจำโตตามจำนวนงานสื่อที่รันพร้อมกันใน instance เดียว (หลาย event ใน webhook เดียวรันข้างกัน และ instance หนึ่งอาจรับหลายคำขอ) วิดีโอ 50 MB ราว 20 งานพร้อมกันก็ถึง 2 GB ถ้าเพดานขนาดสูงขึ้นมาก หรือมีสื่อขาเข้าพร้อมกันจำนวนมาก ต้องกลับมาใช้ทางที่ไม่เก็บทั้งไฟล์ (เช่น multipart ทีละส่วน)
- เวลาแย่ที่สุด: ไฟล์ที่ LINE ให้ได้ทันที (รูป เสียง หรือวิดีโอที่ไม่มีภาพตัวอย่าง) ทุกขั้นถึงเพดาน = 100 + 60 + 10 = 170 วินาที ไม่เกิน `MEDIA_JOB_BUDGET_MS` 255 วินาที และทั้งงานถูกตัดที่ 255 วินาทีเสมอ ต่ำกว่า 0.9 × 300 วินาทีของ webhook ([`timing-budget.spec.ts`](../../src/composition/timing-budget.spec.ts) ตรึงไว้)
- port `Clock` มีเมธอดใหม่ `startTimer` ตัวปลอมยิงตัวจับเวลาเมื่อเวลาถูกเลื่อนถึง (`sleep`, `advance`, `set`) test จึงตัดงานที่ไม่จบได้
- ยังไม่ได้ยืนยันกับ Blob และ LINE จริง: การอัปโหลด Buffer ขนาดรูปจากมือถือผ่าน และ log ทั้งสามขั้นขึ้นบน production ([line-oa-setup](../runbooks/line-oa-setup.md#ทดสอบด้วยมือเมื่อมี-line-oa-จริง))

## จะทบทวนเมื่อ

- Log บน production บอกขั้นที่ค้างได้ชัด (เช่น `stage: download` ที่ซ้ำ) และควรแก้ที่ขั้นนั้นโดยตรง
- เพดานขนาดสื่อขาเข้าเพิ่มขึ้นมาก หรือหน่วยความจำของ function ถูกลด
- `@vercel/blob` เปลี่ยนวิธีส่ง body หรือการลองใหม่
